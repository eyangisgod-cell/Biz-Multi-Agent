## 1. Context

### 1.1 项目背景
Biz-Multi-Agent 是一个面向跨境电商与外贸 B 端企业的多 Agent 业务自动化系统。它基于 Python + AgentScope 多智能体框架，封装主流大模型（豆包、Claude、GPT、Gemini），围绕**选品分析**与**询盘接待**两条业务主线，演示任务编排、工具调用、RAG、共享记忆、可观测链路等架构能力，并通过浏览器自动化（RPA）完成商品上架与数据采集的端到端闭环。

### 1.2 设计目标
| 维度 | 目标 |
|------|------|
| 业务价值 | 选品耗时从人工 4 小时/品类 → 系统 2 分钟；询盘首响从 4-12 小时 → 15 秒 |
| 架构示范 | 一套 AgentScope 多 Agent 框架，覆盖两条垂直业务；展示任务拆解、角色隔离、共享记忆、RAG、链路追踪 |
| 工程标准 | Docker 一键部署；新人 30 分钟跑通 Demo；core 单元测试覆盖率 > 60% |
| 面试/B 端复用 | 业务与框架解耦（替换 Prompt/工具/数据源即可换行业） |

### 1.3 关键干系人
- **业务使用者**：跨境电商运营、外贸业务员
- **系统管理员**：客户公司 IT / 运维，负责部署、配置、密钥管理
- **二次开发者**：项目作者（作者本人 + 阅读源码的求职者）
- **下游消费者**：本项目作为开源面试作品，目标读者为技术面试官与希望借鉴架构的中小 SaaS 团队

## 4. Requirements

### 3.1 用户画像与场景

#### 3.1.1 主要用户角色

| 角色 | 描述 | 主要诉求 | 技能水平 |
|------|------|---------|---------|
| **电商运营** | 跨境电商店铺的选品与上架人员 | 快速找到潜力商品、生成可上架素材 | 熟悉平台规则，不懂代码 |
| **外贸业务员** | 通过 WhatsApp/邮件处理海外客户询盘 | 自动接待、自动报价、自动跟进 | 懂业务英语，不懂技术 |
| **企业管理员** | 客户公司的 IT/系统管理员 | 部署、监控、密钥轮换、合规审计 | 懂基础运维 |
| **二次开发者** | 阅读本项目源码或基于本项目开发的工程师 | 清晰的架构分层、可替换的 Prompt 与工具 | 中高级 Python |

#### 3.1.2 核心用户旅程

**电商选品旅程**（电商运营视角）：
1. 打开 Web 后台 → 进入"新建选品任务"
2. 输入品类关键词（如"蓝牙耳机"）+ 目标平台（美客多墨西哥站）
3. 选择数据源策略（爬虫/CSV/官方 API）+ 期望候选数（默认 Top 20）
4. 点击"开始分析"，页面跳转到任务详情，可实时查看 4 个 Agent 的协作进度（SSE 流式）
5. 2 分钟内收到完整报告，包含 Top 20 候选 + 评分明细 + 多语言标题文案
6. 一键"导出" → Markdown / PDF / JSON

**外贸询盘旅程**（外贸业务员视角）：
1. 客户通过 WhatsApp/邮件发送询盘："Hi, I need 500pcs bluetooth earphone, FOB Shenzhen, target price $8.5, delivery in 30 days"
2. 系统在 3 秒内自动回复 + 15 秒内完成客户分层（A/B/C）
3. 业务员在 Web 后台看到分层结果（B 级）+ 自动草拟的多语言报价单（PI）
4. 点击"确认发送"或"修改" → 系统发出报价单（人工确认机制，A/C 级可直接发送）
5. 系统创建跟进任务：24 小时后提醒"客户尚未回复"，72 小时后自动发送跟进邮件

#### 3.1.3 业务目标量化指标
| 指标 | 当前人工 | 系统目标 | 衡量方式 |
|------|---------|---------|---------|
| 单次选品耗时 | 4 小时 | ≤ 120 秒 | `task.duration.end - start` |
| 询盘首响延迟 | 4-12 小时 | ≤ 15 秒 | `inquiry.first_response_at - received_at` |
| 选品结果 Top N 命中率 | 60%（人工经验） | ≥ 75%（模型评分） | 由人工评估 Top 20 中至少 15 个确为有效候选 |
| 询盘信息提取准确率 | 95%（人工） | ≥ 85%（LLM 自动） | 金样集对比 |
| 客户分层准确率 | 90%（人工经验） | ≥ 80% | 金样集对比 |

### 3.2 功能需求详述（PRD 已详，本次补齐边界与异常）

> 完整功能清单见原 PRD 表 3-1 ~ 3-7。本节补充**边界场景、异常行为、降级路径**。

#### 3.2.1 多模型统一封装层

| 功能 | 正常路径 | 异常路径 | 降级 |
|------|---------|---------|------|
| 统一调用接口 | OpenAI 兼容协议封装 | 上游返回非标准错误码 | 抛 `ModelError`，上层重试 |
| 密钥管理 | 环境变量 + Key 池轮换 | Key 全部失效 | 系统进入"降级模式"，仅返回缓存 |
| 调用限流 | 令牌桶主动排队 | 令牌桶超时 → 上游仍 429 | 切换到备用模型 |
| 多模型路由 | 任务类型 → 模型映射 | 候选模型全挂 | 兜底模型 + 兜底话术 |
| 成本统计 | Token 计费写库 | 计费写入失败 | 异步重试，可丢失单条 |
| 故障降级 | 自动 fallback | Fallback 也失败 | 返回脱敏错误页面 |
| 流式输出 | SSE 每 chunk 推送 | 中断连接 | 客户端断连不影响服务端生成 |

#### 3.2.2 多 Agent 协作框架

| 能力 | 正常路径 | 异常路径 | 降级 |
|------|---------|---------|------|
| 任务拆解 | Orchestrator 拆 3-N 子任务 | 拆解结果循环依赖 | 限制重试 1 次，仍循环则抛错 |
| 角色隔离 | 每 Agent 独立 Prompt + 工具集 | Prompt 注入攻击 | 输入过滤 + 关键词黑名单 |
| 消息总线 | AgentScope 内置消息机制 | Agent 长时间无响应 | 60s 超时强制结束该子任务 |
| 共享记忆 | SharedMemory 读写 | 并发写冲突 | 最后写生效（适合"状态覆盖"语义） |
| RAG 检索 | LlamaIndex + Chroma | 检索为空 | 标注"无知识库依据"，纯 LLM 推理 |
| 异常重试 | Tenacity 指数退避 | 重试 3 次仍失败 | 任务失败 + 通知 + 写入死信队列 |
| 可观测链路 | OpenTelemetry 全链路 | Tracing 上报失败 | 日志降级，不影响业务 |

#### 3.2.3 电商 Agent（边界补齐）

| 功能 | 数据源约束 | 输出约束 |
|------|----------|---------|
| 选品分析 | 关键词 → 平台筛选 → 数据源聚合 | 评分基于多维度加权，非单一指标 |
| 数据抓取 | 三种数据源：CSV / 官方 API / Playwright 爬虫 | 三选一优先官方 API，缺则爬虫兜底 |
| 文案生成 | 平台字数限制硬约束（标题 50/描述 500 等） | 超长自动截断 + 标记提示 |
| 图片描述 | VLM 模型输出 | 必须包含：商品主体 + 场景 + 卖点 |
| 上架自动化 | 仅演示流程 | 演示环境用 mock，不真实上架 |
| 平台规则 | RAG 检索美客多/Shopee/TikTok Shop 规则文档 | 强制引用来源，禁止凭空生成 |
| 竞品分析 | 同品类 Top 50 价格 + 评论 | 评论情感分析做正/负向聚类 |

#### 3.2.4 外贸询盘 Agent（边界补齐）

| 功能 | 输入约束 | 输出约束 |
|------|---------|---------|
| 询盘接待 | WhatsApp/邮件原始文本 | 24h 会话窗口内自动响应 |
| 信息提取 | 客户原始消息 | 至少抽取：产品、数量、目标价、交期、目的地 |
| 报价生成 | 产品库 + 客户信息 | 支持 PI 模板，含 Incoterm 2020 |
| 跟进提醒 | 配置的 cron | 失败重试 3 次，仍失败则标记 |
| 客户分层 | 综合：交易历史 + 询盘规模 + 紧急度 | A/B/C 三级，可人工覆盖 |
| 邮件自动化 | 模板 + 变量 | 失败不重发，避免重复打扰客户 |
| 结构化存储 | SQLite | 单库 < 1 GB，< 50 万条询盘 |

## 5. Rationale（设计决策取舍记录）

### 5.1 为什么选 AgentScope 而不是 LangGraph/AutoGen
- **任务编排表达力**：ReAct 范式已过时，AgentScope 的消息总线 + 角色隔离更匹配多 Agent 场景
- **可观测性原生支持**：与 AgentScope Studio 一体化
- **风险**：AgentScope 仍较新，生态不成熟 → 兜底方案：核心服务以 AgentScope 抽象层封装，业务逻辑可下放到 LangGraph

### 5.2 为什么用 LlamaIndex + Chroma 而非纯向量库
- **LlamaIndex 的 RAG 工具链成熟**：分块、重排序、Query 改写开箱即用
- **Chroma 是轻量级**：单二进制启动，不需要额外服务，匹配 docker-compose 自托管
- **风险**：百万级文档性能下降 → 兜底：切换 Qdrant 或 Weaviate

### 5.3 为什么多模型而非单一模型
- **成本**：把 Opus 用在 Planner、用 Flash 在子任务，成本可降 60%
- **可靠性**：单模型故障不影响系统
- **效果**：不同模型在中文/英文/多模态各有优势，按需调度

### 5.4 为什么 SQLite 而非 PostgreSQL 作为默认
- **MVP 阶段**：单文件部署，零运维
- **未来扩展**：预留 PostgreSQL 切换接口（SQLAlchemy ORM）

## 6. Detailed Design

### 6.1 系统模块图

```
┌───────────────────────────────────────────────────────────────┐
│  表现层  Web 后台 (FastAPI + 简易前端)  CLI (调研/运维)        │
├───────────────────────────────────────────────────────────────┤
│  编排层  Orchestrator Agent 任务拆解 + 调度                   │
├───────────────────────────────────────────────────────────────┤
│  Agent 层                                                       │
│  ├─ 电商线：DataCollector / RAGAgent / Evaluator / Reporter    │
│  └─ 外贸线：IngestionRouter / InfoExtractor / Quoter / Follow-up│
├───────────────────────────────────────────────────────────────┤
│  服务层  模型网关  RAG 检索  通知  调度  浏览器池  邮件         │
├───────────────────────────────────────────────────────────────┤
│  数据层  SQLite  Chroma  文件存储  Redis（可选缓存）             │
├───────────────────────────────────────────────────────────────┤
│  横切关注  日志  链路追踪  限流  重试  配置中心                  │
└───────────────────────────────────────────────────────────────┘
```

### 6.2 关键数据流
1. **电商选品任务**：Orchestrator 接收任务 → 调度 DataCollector（并发拉取多平台）→ 调度 RAGAgent（查平台规则）→ 调度 Evaluator（评分）→ 调度 Reporter（生成报告）
2. **外贸询盘处理**：Webhook 接收消息 → 调度 InfoExtractor → 调度分层 → 调度 Quoter → 业务员确认 → 调度邮件发送 + 跟进任务创建

### 6.3 模块自治
- **每个 Agent 是独立单元**：可单独启停、可 A/B 测试、可灰度
- **服务层无状态**：横向扩展友好
- **数据层支持冷启动**：SQLite 可一键备份/迁移
